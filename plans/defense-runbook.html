Six things that will ruin the demo

Do not redeploy on demo day. make aws-up rebuilds every image from the repos' current main. The stack as it runs is the one that passed 13/13; leave it.

Log in to AWS SSO first. The engine-down scene and every checkpoint use kubectl, which authenticates through the SSO session. An expired session fails mid-scene: aws sso login --profile rokusec before you start.

Present from the CloudFront hosts above. The passkeys are bound to the auth host. They fail from any other name, a local URL or a custom domain.

Press “Limpiar fallos” before the run and after each attack scene. An attacker IP stays blocked for 30 min and Martín's own failures pause him for 15 min; a leftover counter changes the next scene's action.

Run the load scene last. It adds ~16,000 decisions from load-user-*, which push Martín's rows off Diego's Eventos page.

After engine-down, scale back to 3, not 2. The autoscaler's minimum on AWS is 3; restoring 2 makes it add a pod during whatever comes next.

PHASE 1

Morning checks

~10 min

The stack stays up overnight; these confirm it is the one that passed. Each check has a single expected answer.

aws sso login --profile rokusec
cd ~/Documents/UADE/PFI/develop/rba-infra
Checkpoint 1 — pods
kubectl --context rokusec -n rba get pods
kubectl --context rokusec -n demo get pods

All 1/1 Running: decision-service ×3, idp ×2, event-publisher, profile-service, audit-service, audit-api, rabbitmq, prometheus, grafana, kube-state-metrics; demo-banking and demo-kaze in demo.

Checkpoint 2 — the model is loaded
kubectl --context rokusec -n rba logs deploy/decision-service | grep artifact

loaded Freeman artifact /app/artifacts/freeman-0.4.0.json and the supervised logreg-0.2.0. Without them every decision is a fallback.

Checkpoint 3 — the journal is draining
kubectl --context rokusec -n rba logs deploy/event-publisher --tail=5

Lines like published 3/3 event(s), both numbers equal. publishing is stalled means RabbitMQ is unreachable: decisions still answer, but profiles stop learning.

Checkpoint 4 — the starting policy

Console as Diego → Política: Contraseña y passkey siempre · Motor: Monitoreo, version 2.1.0. If the engine is on Activo from a rehearsal, switch it back to Monitoreo.

Checkpoint 5 — one real login

Presenter → Limpiar fallos. Then log in to Roku Bank as Martín in browser 2: the passkey is asked and he lands on the home. Diego's Eventos shows it within a second.

No passkey for Martín in that browser? Issue a code and enroll at /activate on the auth host:

kubectl --context rokusec -n rba exec deploy/idp -c idp -- \
  python -m rba_idp.activation martin@correo.example --tenant roku-bank
PHASE 2

The demo, click by click

~25 min
Set up the screens first (before the audience)
  • Browser 1 — the operator (e.g. Chrome): the RokuSec console. Juan and Diego log in here, one after the other.
  • Browser 2 — the customer (e.g. Safari, or a second Chrome profile): Roku Bank as Martín, and Kaze Labs. Martín's passkey must live in this browser or on the phone you scan with.
  • Browser 2, a hidden tab — the presenter panel. It must be the same browser as Martín: the impossible-travel link opens Martín's login there. Never show this tab.
  • A terminal in rba-infra, logged in to SSO, for the engine-down act.
  • Grafana in a second tab of browser 1, already on Dashboards → RBA → RBA PDP.

To log in again as Martín at any point: bank → Cerrar sesión. If the login page shows “Sesión iniciada”, press its Cerrar sesión too.

A1

Act 1 — The platform, as Juan

  1. Browser 1 → open the console (…cloudfront.net/admin on the auth host).
  2. Email juan@rokusec.example, password, Continuar → Usar passkey.
  3. Sidebar Plataforma → Organizaciones: Roku Bank and Kaze Labs, each with its own logo and login style.
  4. Top of the sidebar, Organización: open the switcher and show both tenants. Leave it on Roku Bank.
  5. Top right → Mi cuenta → Cerrar sesión.

RokuSec is a platform: each organization has its own users, policy and login, and only the platform operator sees them all.

A2

Act 2 — Roku Bank watches before it acts

REQUIRE_MFA
  1. Browser 1: log in as diego@rokubank.example (password, Usar passkey). He lands on Resumen.
  2. Acceso → Política: point at Contraseña y passkey siempre and Motor: Monitoreo. That's how the bank works today.
  3. Browser 2: open Roku Bank. The login wears the bank's brand with “Protegido por RokuSec”.
  4. martin@correo.example, password, Continuar → Usar passkey → the bank's home.
  5. Browser 1: Actividad → Eventos. Top row, Martín: Pidió passkey, and under it El motor: permitido.
  6. Click the row: the reasons (familiar network, device, browser), the score bar, the login's origin.
  7. Actividad → Resumen: the prompts the engine would have saved.

In monitor mode the engine decides and records, but the bank's usual rule still applies. Diego sees what would change before changing anything.

A3

Act 3 — Switch the engine on

ALLOW
  1. Browser 1: Política → Motor: Activo → Guardar → confirm with Guardar.
  2. Count to six (each engine replica picks up the policy within 5 s).
  3. Browser 2: Cerrar sesión, log in again as Martín → straight in, no passkey.
  4. Browser 1: Eventos → the new row: Permitido, risk Bajo.
  5. Optional — Martín on his phone, mobile data: the passkey is asked (new network/device). Only if the phone has his passkey.

The usual login stops paying for the attacks it is not.

A4

Act 4 — A stolen password from Tokyo

REAUTHENTICATE
  1. Presenter tab: Limpiar fallos, then Login desde Tokio → Lanzar. A Lambda in Tokyo logs in with Martín's real password.
  2. The panel shows the attempt stopped at the step-up (REAUTH_REQUIRED).
  3. Browser 1: Eventos → the JP row: Reautenticación, risk Crítico. Open it: hosting network, new country, an OS Martín never uses.

The password was right and it still wasn't enough: the attacker would need Martín's passkey. And since the step-up was never passed, Japan does not become familiar for Martín.

A5

Act 5 — Credential stuffing

REAUTHENTICATEBLOCK the IP
  1. Presenter: Limpiar fallos → Stuffing · ráfaga → Lanzar (one wrong password from Tokyo, Frankfurt and São Paulo).
  2. Browser 2: Martín logs in → asked to re-enter his credentials and use the passkey.
  3. Browser 1: Eventos → Martín's row: Reautenticación, “contraseñas incorrectas desde lugares desconocidos”.
  4. Presenter: Limpiar fallos → Stuffing · sostenido → Lanzar. Wait ~5 s: each region tries 10 wrong passwords, then the real one.
  5. The panel: every region's last attempt is BLOCKED: the right password, refused, because that IP is blocked.
  6. Browser 1: Eventos: the rows from the three IPs, “IP bloqueada por intentos fallidos”.
  7. Browser 2: Martín logs in → passkey, and he's in.
  8. Presenter: Limpiar fallos.

An attacker who knows Martín's address can't lock him out. What gets blocked is the attacker's machine; Martín just confirms with his passkey.

A6

Act 6 — Martín's own typos

BLOCK 15 min
  1. Optional. Browser 2: Martín types a wrong password five times, then the right one → “No pudimos iniciar tu sesión”.
  2. Browser 1: Eventos → Bloqueado, “cuenta en pausa por contraseñas incorrectas propias”: 15 minutes, from his own network.
  3. Presenter: Limpiar fallos before going on.
A7

Act 7 — Impossible travel

REQUIRE_MFA
  1. Presenter (browser 2): Viaje imposible → Abrir login. Martín's login opens “from Japan”.
  2. Log in as Martín → passkey → in.
  3. Browser 1: Eventos → open the row: it is marked Simulado, and the reason is viaje imposible desde el último inicio.

Real impossible travel needs a login from abroad; here the country is injected and the console says so. A simulated login never teaches the profile.

A8

Act 8 — The engine goes down

REQUIRE_MFA
  1. Terminal: kubectl --context rokusec -n rba scale deploy/decision-service --replicas=0
  2. Wait ~10 s. Browser 2: Martín logs in → passkey, never a lockout.
  3. Browser 1: Eventos can't load while the engine is down; that is the point.
  4. Terminal: kubectl --context rokusec -n rba scale deploy/decision-service --replicas=3, then kubectl --context rokusec -n rba rollout status deploy/decision-service.

If the engine fails, nobody is locked out and nobody gets in on a password alone: everyone is asked for the passkey.

A9

Act 9 — Does it work? Efectividad

  1. Browser 1: Actividad → Efectividad: password only vs. passkey always vs. adaptive, on the held-out dataset, with confidence intervals.

Adaptive stops close to what passkey-always stops, while asking for it far less often.

A10

Act 10 — Kaze Labs: another customer, roles

  1. Browser 2: open Kaze Labs. The login is RokuSec's own, “Continuá a Kaze Labs”.
  2. lucas@kazelabs.example (admin), password → Inicio, Proyectos, Configuración: all reachable. Cerrar sesión.
  3. valen@kazelabs.example (viewer) → Proyectos: no “Crear proyecto”; Configuración: refused.

Same platform, a different kind of customer: a company's internal portal, password only with the engine active, and roles that decide what each person can do.

A11

Act 11 — Isolation

  1. Browser 1, still Diego: Directorio → Usuarios: only Roku Bank's people, no Kaze user.
  2. Cerrar sesión; log in as Juan → switcher Organización → Kaze Labs → Usuarios: Kaze's people. Martín exists in both, as two separate accounts.
A12

Act 12 — Load (last)

  1. Browser 1: switch to the Grafana tab (RBA PDP dashboard).
  2. Presenter: Carga → Iniciar (32 clients, 90 s).
  3. Grafana: requests climb to ~160/s, p95 stays around 24 ms against the 200 ms line, replicas go from 3 to 5.

The login waits on memory only; the database is filled behind the answer.

✓

After the last act

  1. Presenter: Limpiar fallos.
  2. Browser 1 as Diego: Política → Motor: Monitoreo → Guardar, ready for another run.
