Four things that will ruin the demo

Start from a deleted cluster. k3d-up.sh reuses an existing cluster, and Postgres keeps its PVC. A cluster created before the RBAC change has no roles rows — create_all adds the tables but cannot populate them, so every login returns ACCESS_DENIED and it looks like the password is wrong. Run k3d-down.sh first, then k3d-up.sh. Checkpoint 5 catches it in five seconds.

Present from localhost:8080. WEBAUTHN_RP_ID is localhost; the passkey step-up fails from any other host or port, including your machine's LAN IP.

Reset before every run. The stuffing steps leave failures in a 24-hour window that keep escalating later logins. A dirty profile changes every action in the script.

Never restart the RabbitMQ pod. See failure modes — it silently destroys queues and drops in-flight events permanently.

PHASE 2

Verify before you trust it

~1 min

Four checks. Each one has failed for real at least once, and each one fails silently — the login page still renders, so nothing looks wrong until a scenario gives the wrong answer in front of the room.

Checkpoint 1 — both model artifacts loaded in the container
kubectl --context k3d-rba -n rba logs deploy/decision-service | grep -i artifact
loaded Freeman artifact /app/artifacts/freeman-0.2.0.json
loaded supervised artifact /app/artifacts/logreg-0.1.0.json (escalate-only, threshold 0.9028)

These paths come from Dockerfile ENV, not from Helm. Running from source never exercises them. If either line is missing, every evaluate returns fallback=true and the whole demo is meaningless.

Checkpoint 2 — the home profile is seeded
kubectl --context k3d-rba -n rba logs deploy/profile-service | grep seed
seeded home profile key=rba:profile:usr_demo
Checkpoint 3 — the async plane is actually moving
kubectl --context k3d-rba -n rba logs deploy/event-publisher --tail=20 | grep published
published 2/2 outbox row(s)

Both numbers must match. published 0/5 means the broker link is down and no profile will ever update again — the log also prints publishing is stalled when that happens.

Checkpoint 4 — every surface answers
curl -s -o /dev/null -w "%{http_code}\n" http://demo.localhost:8080/walkthrough
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/login
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/grafana

Three 200s.

Checkpoint 5 — the RBAC chain is populated
kubectl --context k3d-rba -n rba exec deploy/postgres -- \
  psql -U rba -d rba_idp -c \
  'select r.name, r.application_id, count(rp.permission_id) as perms
     from roles r left join role_permissions rp using (role_id)
    group by 1, 2 order by 2, 1;'
      name       |  application_id   | perms
-----------------+-------------------+-------
 customer        | demo-banking-app  |     3
 viewer          | demo-banking-app  |     2
 platform-admin  | idp-admin-console |     4

Four roles. Zero rows means a stale database — the schema is created on boot but the seed only inserts into an empty table set, so an upgraded cluster gets the tables without the data. Every login will return ACCESS_DENIED, which reads on stage as a broken password. The fix is k3d-down.sh && k3d-up.sh; there is no migration tooling.

PHASE 4

Reset

~30 s

Run this immediately before presenting, and again between rehearsals.

bash rba-infra/scripts/reset-demo.sh
Checkpoint — it must print exactly this
pristine seed: 98 0 203.0.113.10

98 successful logins, 0 failures, only the home IP seen. Anything else and the profile is dirty.

Why a script rather than one redis-cli DEL: the seed is written SET NX, so deleting the key and restarting profile-service re-seeds it — but an in-flight decision event can land after the reseed and re-pollute the blob. The script retries until the profile matches the pristine seed exactly. During development this silently corrupted three measurements before anyone noticed; they showed score 0.5000 with a low_history reason, which is what an empty profile scores.

PHASE 5

The live script

~8 min

Two browser windows. Left: the walkthrough at demo.localhost:8080/walkthrough. Right: the admin Decisions view at localhost:8080/admin, already signed in as the admin — that is where the reasons live, and it is what turns each result into an explanation.

Every step is the same three clicks: pick the scenario on the left, sign in as demo@example.com / demo-password, then read the newest row on the right. Order matters — it is the argument, not a list.

1

Click New country → sign in

Germany / Deutsche Telekom. Runs first, from a cold seed, so the travel rule stays quiet.

Expect a surprise in admin: the score reads 0.0000 and the reason is supervised_second_opinion — not a novel-signal reason. Freeman abstains here; see reading the score.

"Two models run on every login. The likelihood-ratio model says this is fine — the device, browser and network are all still familiar, and novelty has a ceiling while familiarity doesn't. The supervised model disagrees. It can raise the bar; it can never lower it."

Click Home → sign in

"Same system, same user, one second later. Adaptive means most logins feel like nothing happened."

Click Teleport → sign in — immediately after step 2

REQUIRE_MFA
Click VPN → sign in

United States / Cloudflare. Reason is vpn_or_hosting — a hosting ASN sidesteps the physics check, so it's judged as an untrusted network instead.

"The evasion is anticipated. Skipping the travel rule doesn't buy the attacker anything."

5

Credential stuffing — burst

REAUTHENTICATE
Click Credential stuffing — burst → wait ~10 seconds → sign in

Fires four wrong passwords, then hands you the login page. Deliberately from the user's own country and ASN — a residential proxy, which is what stuffing actually looks like.

The number to point at: the score is 0.0000 and the level is LOW, while the action is REAUTHENTICATE. Freeman sees nothing wrong. The rule does.

"This is the case the model structurally cannot catch. A failed attempt from the attacker's own machine just looks like an ordinary login. The count is what gives it away — and notice the score never moved. The rule raises a floor; it never rewrites the model's number."

6

Credential stuffing — lockout

BLOCK
Click Credential stuffing — lockout → wait ~15 seconds → sign in

Twelve wrong passwords. Past the lockout band the answer is to stop serving the account rather than offer a challenge — no MFA prompt is shown at all.

The reason reads 11 failed logins in the last 24h (lockout threshold 10). Eleven, not twelve — see failure modes. Still well past the threshold.

"Four distinct actions from one policy, and the customer never saw a risk score at any point."

The one timing trap

On steps 5 and 6, the wrong passwords travel the async path — PDP → outbox → RabbitMQ → profile-service → Redis — before the count is visible to the next decision. Sign in too fast and you get ALLOW, which is exactly backwards from the point you're making. Count to ten. If you want certainty instead of a count, run this until it prints 4 (or 11):

kubectl --context k3d-rba -n rba exec deploy/redis -- redis-cli GET rba:profile:usr_demo \
  | python3 -c 'import json,sys;print(len(json.load(sys.stdin).get("failed_login_ts",[])))'
PHASE 6

Prove authorization, not just authentication

~3 min

Everything above is about whether you get in. This is about what you may do once you are in — RF-21, and the half of the scope statement that says control de acceso basado en roles. Use a second browser profile or a private window so both users stay signed in at once.

The chain is user → group → role → permission. The bank never sees any of it: GET /session hands it a flat list of resource:operation strings and it gates on those. Every screen below prints that list at the bottom of the page, which is the fastest way to show what changed.

Identical login, identical scoring, identical ALLOW in admin. Balances render. The "Send money" button is not there, and the footer reads account:read  transaction:read.

"Same user experience, same risk decision. Authentication said yes to both of these people. Authorization is a separate question, and it is answered separately."

Revoke it live

no re-login
Admin as admin@example.com → Roles → customer → untick transfer:create → Save → reload the customer's bank tab

The button disappears without a sign-out. Permissions are resolved inside the session lookup on every request rather than baked into the token at login, so there is no window in which a revoked role still works.

"This is the property that makes the model worth having. Revocation takes effect on the next request, not on the next login — and nobody had to remember to invalidate a token."

Put it back before the next rehearsal — re-tick transfer:create, or re-run k3d-down.sh && k3d-up.sh. reset-demo.sh only resets the risk profile in Redis; it does not touch the directory in Postgres.

If every login says ACCESS_DENIED

The database predates RBAC and has no roles rows. See checkpoint 5. It is not the passwords.

PHASE 7

Break it on purpose

~4 min

Two demonstrations that a tribunal is more likely to ask about than any of the happy paths: what happens when the risk engine is down, and how do you deploy this without locking anyone out on day one. Both are policy positions with code behind them, not slideware.

7a — The PDP disappears mid-demo

An IdP that hard-fails when the scorer is unreachable has traded an availability incident for a total outage. One that waves everyone through has silently removed the control. RNF-03 names both as wrong, so the answer is neither: ask for a step-up.

kubectl --context k3d-rba -n rba scale deploy/decision-service --replicas=0
kubectl --context k3d-rba -n rba rollout status deploy/decision-service --timeout=60s

Now sign in as demo@example.com from Home — the scenario that was ALLOW a minute ago. You get the passkey prompt instead, and it works: you end up inside the bank.

Where the evidence is
kubectl --context k3d-rba -n rba logs deploy/idp | grep "PDP unavailable"
PDP unavailable, degrading to REQUIRE_MFA for user_id=usr_demo: ...

Point at the log, not at admin. A degraded login is deliberately not written to the decision store — that store lives behind the service that just failed to answer. In this cluster the audit read path is also proxied through decision-service, so the Decisions tab will be unavailable for as long as it is scaled to zero. Say that out loud before someone notices it and reads it as a bug.

The guarantee is enforced by the type, not by discipline: the setting is pdp_unavailable_action: Literal["REQUIRE_MFA", "REAUTHENTICATE"]. ALLOW and BLOCK are not expressible, so no configuration mistake can turn an outage into open access or a mass lockout.

kubectl --context k3d-rba -n rba scale deploy/decision-service --replicas=2
kubectl --context k3d-rba -n rba rollout status deploy/decision-service --timeout=2m

7b — Monitor-only mode

The honest answer to "how would a bank actually roll this out". Score every login, record it, publish it, and return ALLOW to the application anyway — so you can measure what the engine would have done to real traffic before it does it to anyone.

Flip it in the admin console's Policy tab (today a JSON textarea over the bundle) by setting defaults.monitor_only to true and saving. Scriptable equivalent:

A=$(curl -s http://localhost:8080/login -H 'content-type: application/json' -d '{
  "email":"admin@example.com","password":"admin-password",
  "application_id":"idp-admin-console","ip_address":"203.0.113.10",
  "asn":"13335","country":"AR","device_type":"desktop",
  "os":"macOS","browser":"Chrome"}' | jq -r .session.token)

curl -s http://localhost:8080/admin/api/policy -H "Authorization: Bearer $A" \
  | jq '.defaults.monitor_only = true' \
  | curl -s -X PUT http://localhost:8080/admin/api/policy -H "Authorization: Bearer $A" \
      -H 'content-type: application/json' -d @- | jq '.defaults.monitor_only'

Then re-run Credential stuffing — lockout, the step that gave BLOCK in phase 5.

SurfaceWhat it shows
The customerSigns straight in. No challenge, no block, no hint that anything was evaluated.
Admin → DecisionsThe row still reads BLOCK, with the same reasons, plus a monitor_only reason recording that it was not enforced.
Grafanarba_decisions_total counts the row under enforced="false".

"This is what you turn on first. It runs for a month, you look at how many real customers would have been challenged or blocked, you retune the bands, and only then do you turn it off. Nothing about the engine changes when you do — the scoring, the reasons and the record are identical. The only thing that changes is what the application is told."

It is editable at runtime and hot-reloads the PDP (RNF-05), and it can be set per application as well as globally, so one tenant can go live while the others stay in monitor. Turn it back off before the next rehearsal or phase 5 will look broken.

One asymmetry worth being able to explain

Monitor mode also suppresses fallback_action — if the scorer breaks while a tenant is being monitored, the tenant keeps getting ALLOW. A scorer outage is not a reason to start acting on someone who explicitly asked not to be acted on. The RNF-03 guarantee in 7a still holds, because it lives at the IdP, where the PDP's silence makes monitor mode unknowable.

If someone asks how the pieces combine: rules and the second opinion each name a floor, the most severe one wins, and nothing can ever lower an action or overwrite risk_score — that number stays Freeman's. Step 5 is the visible proof: LOW level, BLOCK-adjacent action, score untouched at zero.

Reading the score

The two numbers that look odd in the Decisions list are both correct, and both worth being able to explain cold.

CaseSum of LLRsScoreReading
Brand-new user, nothing known0.0000.5000Abstains — no information
Usual home login−56.8990.0000Overwhelmingly familiar
New country + new ASN−31.3680.0000Still familiar on balance
New country + ASN + IP + OS−1.7680.1458Novelty finally competitive

0.50 is not "medium risk" — it is "no information". Freeman is a likelihood ratio: log P(value | population) − log P(value | this user). With an empty profile the user model falls back to the population prior, every term is exactly zero, and the sigmoid returns 0.5. Under this app's bands that lands in HIGH, so a first-ever login is challenged because nothing is known about it — a policy stance, not a model finding.

0.00 is saturation, not a bug. A usual login sums to −56.9; the sigmoid of that is about 2×10−25.

Novelty has a ceiling; familiarity does not. An unseen value contributes exactly log((history + β)/β) — +3.025 on the 98-login seed, identical for every signal, however exotic the value. A familiar signal contributes about −12 and keeps growing with history. So two novel signals (+6) lose to three familiar ones (−36), and an established user cannot be pushed over the line by novelty alone. That asymmetry is the whole argument for the supervised second opinion, and step 1 is where it shows on screen.

Why you must not restart RabbitMQ

The broker's node name is derived from the pod hostname — rabbit@rabbitmq-79667c469-q9sqd. Mnesia stores queues per node name, so a recreated pod comes back as a different node with an empty broker, even though the PersistentVolumeClaim reattaches; the old node's directory is orphaned on the volume. Every queue and binding is gone. Anything the publisher sends before the consumers reconnect and re-declare their queues is discarded by the exchange, and because the outbox has already marked those rows published, they are never retried. That is permanent, silent data loss.

It is survivable in rehearsal and fatal on stage. The durable fix is a StatefulSet or a fixed RABBITMQ_NODENAME; neither is applied yet.
