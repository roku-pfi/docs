Six things that will ruin the demo

Do not redeploy on demo day. make aws-up rebuilds every image from the repos' current main. The stack as it runs is the one that passed 13/13; leave it.

Log in to AWS SSO first. The engine-down scene and every checkpoint use kubectl, which authenticates through the SSO session. An expired session fails mid-scene: aws sso login --profile rokusec before you start.

Present from the CloudFront hosts above. The passkeys are bound to the auth host. They fail from any other name, a local URL or a custom domain.

Press “Limpiar fallos” before the run and after each attack scene. An attacker IP stays blocked for 30 min and Martín's own failures pause him for 15 min; a leftover counter changes the next scene's action.

Run the load scene last. It adds ~16,000 decisions from load-user-*, which push Martín's rows off Diego's Decisiones page.

After engine-down, scale back to 3, not 2. The autoscaler's minimum on AWS is 3; restoring 2 makes it add a pod during whatever comes next.

Morning checks

~10 min

The stack stays up overnight; these confirm it is the one that passed. Each check has a single expected answer.

aws sso login --profile rokusec
cd ~/Documents/UADE/PFI/develop/rba-infra
Checkpoint 1 — pods
kubectl --context rokusec -n rba get pods
kubectl --context rokusec -n demo get pods

All 1/1 Running: decision-service ×3, idp ×2, event-publisher, profile-service, audit-service, audit-api, rabbitmq, prometheus, grafana, kube-state-metrics; demo-banking and demo-kaze in demo.

Checkpoint 2 — the model is loaded
kubectl --context rokusec -n rba logs deploy/decision-service | grep artifact

loaded Freeman artifact /app/artifacts/freeman-0.4.0.json and the supervised logreg-0.2.0. Without them every decision is a fallback.

Checkpoint 3 — the journal is draining
kubectl --context rokusec -n rba logs deploy/event-publisher --tail=5

Lines like published 3/3 event(s), both numbers equal. publishing is stalled means RabbitMQ is unreachable: decisions still answer, but profiles stop learning.

Checkpoint 4 — the starting policy

Console as Diego → Política: Base: passkey siempre · Motor: monitor, version 2.1.0. If the engine is on Activo from a rehearsal, switch it back to Monitor.

Checkpoint 5 — one real login

Presenter → Limpiar fallos. Then log in to Roku Bank as Martín from the demo machine: the passkey is asked and he lands on the home. Diego's Decisiones shows it within a second.

PHASE 2

The script

~20 min

Two windows side by side: Martín's browser (light, the bank) and Diego's console (dark). The presenter panel lives in a third tab and is never shown as product.

1

Monitor mode

REQUIRE_MFA
Martín logs in to Roku Bank.

Martín: passkey, as every bank login today. Diego: the decision shows enforced REQUIRE_MFA (the base policy) and the engine's own verdict ALLOW, low risk. Resumen counts it as a prompt the engine would have saved.

The engine watches before it acts: the bank sees what it would decide without changing anything for its customers.

2

Switch to active

ALLOW
Diego: Política → Motor → Activo → Guardar. Wait ~6 s, then Martín logs in.

Martín: straight in, no passkey. Diego: engine ACTIVE, ALLOW, LOW; the reasons say familiar network, device and browser.

The usual login stops paying for the attacks it is not.

3

New device or network

REQUIRE_MFA
Martín logs in from the phone on mobile data (only if the phone has its passkey).

Martín: passkey. Diego: the network or device is new for him; the score rises and the step-up is asked. Passing it teaches the profile the new context (ADR-0042).

4

Login from Tokyo

REAUTHENTICATE
Presenter → Login desde Tokio. A Lambda in ap-northeast-1 uses Martín's real password.

Diego: JP, a hosting network, a new OS: CRITICAL. Roku Bank steps CRITICAL up instead of blocking (policy 2.1.0), so the attacker is asked for a passkey they do not have; the step-up is never completed and teaches the profile nothing.

A stolen password is not enough: the answer is the passkey, and the attempt leaves no trace in Martín's profile.

5

Stuffing burst

REAUTHENTICATE
Presenter → Limpiar fallos, then Stuffing · ráfaga (one wrong password from each of three regions). Then Martín logs in.

Martín: asked to re-enter his credentials and pass the passkey. Diego: failed_login_burst: 3 wrong passwords from places Martín never uses.

6

Sustained stuffing

BLOCK the IP
Presenter → Limpiar fallos, then Stuffing · sostenido. Each region tries 10 wrong passwords and then Martín's real one. Then Martín logs in.

Panel: every region ends in BLOCKED: the IP passed its threshold, so even the right password is refused (source_blocked). Martín: asked for his passkey, and gets in. Diego: REAUTHENTICATE on Martín's login, never a block.

An attacker who knows Martín's address cannot lock him out. What gets stopped is the attacker's machine (ADR-0045).

7

Martín's own typos

BLOCK 15 min
Optional. Martín types a wrong password five times from his laptop, then the right one.

Martín: “No pudimos iniciar tu sesión”. Diego: account_cooldown: five failures from a network he uses pause the account for 15 minutes, like a phone's PIN delay. Press Limpiar fallos to go on.

8

Impossible travel

REQUIRE_MFA
Presenter → Viaje imposible, in Martín's browser. Log in as Martín.

Martín: passkey. Diego: impossible_travel, marked simulado; the presenter overrides the country, so the login never teaches the profile Japan.

Real impossible travel needs a login from abroad; here the country is injected, and the console says so.

9

Engine down

REQUIRE_MFA
kubectl --context rokusec -n rba scale deploy/decision-service --replicas=0

Martín logs in: passkey, never a lockout (the IdP's fallback, ADR-0028). Diego's Decisiones cannot list while the engine is down, which is the point of the scene. Restore:

kubectl --context rokusec -n rba scale deploy/decision-service --replicas=3
kubectl --context rokusec -n rba rollout status deploy/decision-service
10

Roles at Kaze Labs

Lucas logs in to Kaze Labs, then Valen.

Lucas (admin) reaches Inicio, Proyectos and Configuración. Valen (viewer) reads projects, has no form to create one, and gets 403 on Configuración. Kaze's own policy: password only, engine active.

11

Isolation

Juan in the console switches between organizations; Diego cannot.

Diego sees only Roku Bank's users and decisions; asking for Kaze Labs as Diego is refused. Martín has an account in each tenant (martin@correo.example at the bank, martin@kazelabs.example at Kaze), two separate users.

12

Load

Presenter → Carga (32 clients, 90 s). Watch Grafana and Resumen.

About 160 decisions per second, no errors, p95 around 24 ms against the 200 ms target; the decision service grows from 3 to 5 replicas. Last, because it floods Decisiones.

The login waits on memory only: the database is filled behind the answer (ADR-0044).
